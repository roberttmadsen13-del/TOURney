Row Level Security
Every Table, Every Policy
Policy clauses cited verbatim from migration SQL. Severity = worst policy on that table.
SAFE tournaments — public read + owner write migration 001
Two policies. SELECT: "public read tournaments" — TO anon USING (true) — all tournaments visible to everyone. Intentional: tournament discovery is public. Write: "owner manage tournament" — TO authenticated USING (auth.email() = owner_email) — scoped to owner email. Solid.
RiskPublic tournament data readable by anon. Intended. No sensitive fields on this table. No action needed.
SAFE tournament_admins — public read migration 001 + 004
"public read tournament_admins" — TO anon USING (true). Needed for client-side admin gate checks. Migration 004 added email-based admin write: auth.email() = owner_email OR EXISTS(tournament_admins WHERE player_id = auth.uid()). Write properly scoped.
RiskPlayer IDs + tournament IDs visible to public. Acceptable — these aren't secret. Write path locked down correctly.
SAFE settings — owner or admin write only migration 003 + 004
Migration 003 dropped all prior wide-open write policies and replaced with: "owner or admin write settings" — TO authenticated USING (auth.email() = (SELECT owner_email FROM tournaments WHERE id = settings.tournament_id) OR EXISTS (SELECT 1 FROM tournament_admins ta WHERE ta.tournament_id = settings.tournament_id AND ta.player_id = auth.uid())). Migration 004 re-applied same pattern after email-based admin model. Read policy not visible in migrations — likely anon read (course pars, round state are public anyway).
RiskNone. Write scoped correctly. Read is public settings data.
CRITICAL invitations — anon update owns nothing migration 005
"anon update own invitation" — FOR UPDATE TO anon USING (true) WITH CHECK (true). Despite the name "own invitation," there is no ownership predicate. Any unauthenticated user can UPDATE any row in the invitations table — any tournament, any player. Attack: enumerate invitation IDs (readable via "anon read invitations" which is also USING (true)), then update status = 'declined' for all of a rival's invitees, or flip status = 'accepted' for uninvited emails.
Fix — Day 1 Option A (quick): Add USING (email = current_setting('request.jwt.claims', true)::json->>'email') — only works if anon callers pass a JWT with their email, which they don't. Option B (right): Replace with an edge function accept-invitation that takes {invitation_id, token}, validates a per-invitation access_token column (UUID generated on invite creation), and performs the update as service_role. Drop the anon update policy entirely. 2-hour fix.
HIGH invitations — authenticated users manage all invitations migration 005
"auth manage invitations" — FOR ALL TO authenticated USING (true) WITH CHECK (true). Any logged-in user (a player who signed up for any tournament) can INSERT, UPDATE, or DELETE any invitation across all tournaments. Attack: authenticated player A deletes all invitations for tournament B. Or inserts fake invitations to collect RSVPs.
Fix — Day 1 Replace USING (true) with USING (EXISTS (SELECT 1 FROM tournaments t WHERE t.id = invitations.tournament_id AND (t.owner_email = auth.email() OR EXISTS (SELECT 1 FROM tournament_admins ta WHERE ta.tournament_id = t.id AND ta.player_id = auth.uid())))). Same pattern already proven in settings migration 003.
HIGH player_accounts — billing data open to anon migration 005
"anon read player_accounts" — FOR SELECT TO anon USING (true). The player_accounts table stores plan, billing_status, billing_expires_at, billing_ref. All rows readable by unauthenticated users. Any visitor to the site can query Supabase with the anon key and enumerate every player's subscription tier and billing status.
Fix — This Week Replace anon read with: FOR SELECT TO authenticated USING (email = auth.email()) — users see only their own row. For the player upgrade flow, use a server-side lookup or pass the tier via the JWT claim. The Stripe webhook (already service_role) is unaffected.
SAFE players + scores — hardened per migrations 008–011 migrations 008, 009, 011
Migration 008 (security_rls_hardening) and 009 (fix_rls_self_join_bugs) tightened players and scores. Migration 011 (trash_talk_rate_limit_and_player_scoped_insert) added player-scoped INSERT — players can only insert scores for their own player record. Migration 010 tightened push_subscriptions and tournament_admins. These were the right moves.
StatusNo action needed. The hardening migration chain (008→011) addressed the main write-path issues on core game tables.
XSS Surfaces
Every innerHTML Assignment
grep -rn 'innerHTML' across all .html files. test.js XSS suite: 0 failures, 4 warnings. esc() helper (feed.html:658) uses DOM entity-encode pattern — safe.
MEDIUM scoreboard.html:1096 — _parseMentions(p.message) to innerHTML
el.innerHTML = _trashPosts.map(p => `<div class="trash-post-body">${_parseMentions(p.message)}</div>`). p.message is DB-sourced trash talk (user-submitted text). _parseMentions applies a regex to wrap @mentions in <span class="mention"> tags — but it does NOT escape the base text before the regex runs. A player who submits <img src=x onerror=alert(document.cookie)> as a trash talk message would have that rendered verbatim into innerHTML for every player viewing the scoreboard.
Fix — This Week Escape before parsing: function _parseMentions(raw) { const safe = esc(raw); return safe.replace(/@([A-Za-z][A-Za-z '.'-]*[A-Za-z])/g, '<span class="mention">@$1</span>'); }. The esc() helper already exists. One line change.
MEDIUM admin.html:2044 + 2194 — url variable to innerHTML
test.js flags both lines: innerHTML interpolates url — verify safe. The url variable at these lines likely references a tournament logo URL or image URL sourced from the settings table. If admin-editable (they are — settings are writable by admins), an admin could set a logo_url to javascript:alert(1). HTML renders it into an <img src> or similar. javascript: in src/href attributes bypasses most sanitizers.
Fix — This Week At both sites: validate URL before interpolation. function safeUrl(u) { try { const p = new URL(u); return (p.protocol === 'https:' || p.protocol === 'http:') ? u : ''; } catch { return ''; } }. Or use setAttribute('src', url) instead of innerHTML — browser won't execute javascript: in src attributes set programmatically.
LOW course.html:377 — list (local rules) to innerHTML
document.getElementById('localRulesContent').innerHTML = `<ul class="rule-list">${list}</ul>`. list is built from settings table (local rules text). This is admin-controlled input — if an admin injects HTML, they're XSSing themselves. Not a meaningful attack vector for a single-owner platform. No external attacker path.
RiskSelf-inflicted admin XSS only. Low priority. Could sanitize with DOMPurify if the field becomes user-facing. No action needed pre-launch.
SAFE profile.html:351 — tierClass, tierLabel to innerHTML
tierEl.innerHTML = `<span class="tier-pill ${tierClass}">${tierLabel}</span>`. test.js warns because it sees variable interpolation. Both tierClass and tierLabel are derived from TIER_MAP — a hardcoded local constant object, not DB data. Not a real XSS surface.
StatusFalse positive from test.js pattern matching. No action needed. Could add to SAFE_PATTERNS list in test.js to suppress the warning.

Auth Gates
Platform / Admin / Player
Platform Gate (platform.html:153)

const PLATFORM_EMAIL = 'robert.t.madsen13@gmail.com' hardcoded client-side. The gate logic: check email against constant, then call sb.auth.signInWithPassword({ email, password }). The client-side email check is a cosmetic pre-filter — an attacker can remove it in DevTools and call signInWithPassword directly with any email. However: the actual Supabase auth still requires the correct password. Any DB queries in platform.html run under the authenticated session, so RLS applies. The risk is: someone could attempt to brute-force the Supabase account password now that the email is known. Email is in plaintext in the HTML source.

Risk: LOW-MEDIUM. Supabase rate-limits signInWithPassword. Real attack surface is the exposed email enabling targeted phishing / credential stuffing. Consider: move to magic link auth for platform, removing password attack surface entirely. Not blocking pre-launch.

Admin Gate (tournament_admins table)

Admin access checks against tournament_admins table — populated by owner, verified against auth.uid() in RLS. Migration 004 replaced the old is_admin boolean on the players table (migration 006 dropped it). The current model is solid: admin status lives in a separate table, write-protected by owner/admin RLS, and verified server-side. Client-side is_admin checks are for UX gating only (hide/show UI). Actual data writes go through Supabase RLS.

Risk: LOW. Architecture is correct. No action needed.

Player Score Submission Gate

Migration 011 (player_scoped_insert) added a WITH CHECK that binds score INSERTs to the authenticated user's player record. Players cannot submit scores for other players at the DB level. Offline score queue (localStorage bova_offline_queue) could be tampered client-side — a player could modify stored scores before sync. However, on sync the INSERT hits RLS which validates player_id = auth.uid() mapping. The tampering risk is: a player modifying their own queued scores (changing gross_score values). That's a data integrity issue, not a security breach — and it's only their own scores.

Risk: MEDIUM (integrity, not security). Pre-launch: consider server-side score validation (reject scores outside reasonable range, reject backdated submissions past round close). Post-launch item.

MEDIUM CSP unsafe-inline in script-src nullifies XSS protection
Current CSP verbatim: default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https:; connect-src 'self' https://*.supabase.co wss://*.supabase.co; frame-ancestors 'none';. The 'unsafe-inline' in script-src means the browser will execute any inline <script> tag, including ones injected by XSS. CSP provides zero protection against script injection while this flag is set. Reason it exists: all JS is inline in .html files (no bundler), so nonces/hashes would require a build step.
Fix — Pre-Launch Move all JS to external .js files (one per page or a shared bundle). Then: remove 'unsafe-inline' and add a deployment-time nonce via Vercel Edge Middleware. Or: generate SHA-256 hashes for each script block at build time and add to CSP. The nonce approach requires Vercel Pro (edge functions on every request). The hash approach works on free tier but breaks whenever JS changes. Recommendation: external JS files + remove unsafe-inline. 2-day refactor.

Edge Functions
supabase/functions/ — Auth Pattern Audit
SAFE create-checkout — auth-gated correctly
Reads Authorization header, returns 401 if absent. Creates Supabase client with caller's auth header, calls supabase.auth.getUser(), returns 401 if no valid user. Only proceeds to Stripe session creation for verified authenticated users. CORS OPTIONS handled with Access-Control-Allow-Origin: * — acceptable for a public-facing API that requires auth tokens anyway.
StatusSolid. No action needed.
SAFE stripe-webhook — signature verified
Reads stripe-signature header, returns 400 if absent. Calls stripe.webhooks.constructEventAsync(body, sig, webhookSecret) — cryptographic signature verification. Event must be signed by Stripe's private key. DB writes use SUPABASE_SERVICE_ROLE_KEY (bypasses RLS by design — webhook writes billing status directly). Handles checkout.session.completed and customer.subscription.* events.
StatusCorrect pattern. Service role usage is appropriate here — webhook is the authoritative billing source.
HIGH send-install-email — no auth check whatsoever
Function reads player.email and player.tournament_id from the POST body and sends an email via Resend API. No Authorization header check. No Supabase auth validation. Any HTTP caller who knows the function URL can send an install email to any address with any tournament context. Attack vectors: (1) spam — send thousands of emails through your Resend account, burning your sending reputation and quota. (2) Phishing — craft a malicious install email that links to a fake PWA. (3) Harassment — spam specific players.
Fix — Day 1 Add auth check at the top (same pattern as create-checkout): 
const authHeader = req.headers.get('Authorization');
if (!authHeader) return new Response('Unauthorized', { status: 401 });
const supabase = createClient(url, anonKey, { global: { headers: { Authorization: authHeader } } });
const { data: { user }, error } = await supabase.auth.getUser();
if (error || !user) return new Response('Unauthorized', { status: 401 });
Then verify the caller is the tournament owner or admin before allowing the send. 30-minute fix.
