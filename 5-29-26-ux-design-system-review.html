Reference Design — /player dashboard + /create flow

Both pages locally re-declare the same palette inside their own :root. That palette is now the canonical TOURney design system. It looks like this:

  • Palette: --ink:#0f0a05 body, --surface:rgba(245,237,224,0.05) translucent cream tint for cards, --gold:#c09030, --gold-l:#d4a840 hover, --gold-p:#e8cc80 peach-gold for highlights, --cream:#f5ede0 primary text, --muted:rgba(245,237,224,0.5).
  • Borders: 1px solid rgba(245,237,224,0.13) — cream-tinted at 13% opacity. NOT gold-tinted. This is the single biggest visual signature of the look.
  • Typography: Barlow Condensed for nav + section eyebrows + CTAs. Playfair Display italic for accent words inside titles (e.g. "Create Account"). DM Mono for all data surfaces (stat values, score cells, timestamps, slugs). Barlow regular for body copy.
  • Cards/Surface: Translucent cream over dark ink. border-radius:14px. Hover lifts border-color to --gold (no shadow, no scale).
  • Stat tiles (player dashboard): Flex row, value left-aligned in Playfair, label right-aligned in DM Mono uppercase 0.6rem with 0.16em letter-spacing.
  • Buttons: Primary = full-width gold (background:var(--gold); color:var(--ink)). Secondary = ghost (background:none; border:1px solid var(--border); color:var(--cream)). Hover bumps border to --gold.
  • Section labels: DM Mono, 0.58rem, uppercase, 0.18em letter-spacing, gold color, with a trailing 1px divider line.
  • Sticky nav: dark backdrop with backdrop-filter:blur(8px) + 1px bottom border. Brand mark + nav-right pills.
  • Empty states: Surface card with inline SVG flagstick icon, Playfair headline with italic accent word, Barlow body, gold CTA pill — pattern lives in player.html .empty.

Source files: player.html L22–26 (palette), create.html L21–22 (matching palette), player.html .empty / .stat-cell / .list-row (canonical components).

Typography System — Current State

TOURney has a well-defined three-font stack, consistently loaded via Google Fonts on all tournament pages (scorecard.html L21):

  • Playfair Display (serif) — Headings, hero titles, large display numbers. Italic variant for emphasis. Present on scorecard, home, 404.
  • Barlow Condensed — Navigation links, CTAs, buttons, eyebrow labels. Weight range 300–800. Universally applied across all pages.
  • DM Mono (monospace) — Data labels, dates, small eyebrows, score metadata. Present on scorecard setup labels, scoreboard .score-cell, platform bug rows. This is the key reference font.
  • Barlow (regular) — Body copy. 300–500 weight range.

Typography consistency grades: Strong — font stack is coherent. The gap is not which fonts are used but where they are applied. DM Mono needs broader adoption across data-heavy components (score tables, stat blocks, metadata rows) to match the reference aesthetic.

Prior review note (5-19-26 bugs review, L229): "Barlow Condensed + DM Mono + Playfair Display is the intentional TOURney brand system. Not a defect." — confirms this is the right stack, just under-applied.

§ Second Opinion
Independent Code Audit — Claude Sonnet 4.6 · May 29, 2026
Fresh read of tokens.css + tournament pages. Several findings contradict or sharpen the §Review above. Plan P1 needs rewriting before execution.
CORRECTION — tokens.css is NOT missing dark tokens

The §Review table lists --surface, --text, --gold-dim, --gold-light as MISSING from tournament pages. This is misleading — all four tokens exist in tokens.css with correct dark values right now:

  • --bg: #0d0a05 ✓
  • --surface: #151009 ✓
  • --card: #1c140a ✓
  • --text: #e8dcc8 ✓
  • --muted: #7a6a54 ✓
  • --gold-dim, --gold-light, --card2 ✓

The problem is that tournament pages override those tokens with light values in inline :root blocks. Plan P1 as written ("expand tokens.css") does not fix this — tokens.css already has what it needs. P1 should be: remove per-page light :root overrides and let tokens.css cascade.

NEW FINDING — --font-mono does NOT map to DM Mono

tokens.css defines:

--font-mono: 'Consolas', 'Monaco', monospace;

DM Mono is imported in the Google Fonts URL at the top of tokens.css but never assigned to --font-mono. Any selector using font-family: var(--font-mono) renders Consolas, not DM Mono. The Plan step that says "add DM Mono to data selectors via var(--font-mono)" will silently produce the wrong font unless this token is fixed first. Fix: update tokens.css --font-mono to 'DM Mono', 'Consolas', monospace.

CORRECTION — Plan P1 execution must change

The §Plan P1 says: "Edit tokens.css. Override :root. Verify each page renders dark background." This is the wrong file to edit. tokens.css :root already has dark values. Editing it again has no effect.

Correct P1 execution: grep all tournament HTML files for inline :root { --bg blocks and delete them. The dark theme is already defined and waiting. The light override is the only blocker. One grep + delete per file, no tokens.css touch needed.

Also: tokens.css comment explicitly says "Tournament-specific brand colors override by setting CSS custom properties on :root via tourney-init.js." If a tournament legitimately wants a light theme, tourney-init.js is the right override mechanism — not inline :root. The plan should wire this, not work around it.

NEW FINDING — --green divergence is worse than stated

The §Review flags --green:#2a7a20 vs #1a4010 as a minor token drift. The actual situation: tokens.css defines --green: #27ae60 (standard emerald). The values in admin/scorecard are hardcoded hex — not token references. Those pages are ignoring var(--green) entirely and hardcoding different values inline. This is a token bypass, not a token drift. Any future token update won't propagate to those elements.

NEW FINDING — --cream orphan token

tokens.css defines --cream: #f0e6cc — not documented anywhere in the §Review, not referenced in the plan. This is likely the intended light-surface value. If a light mode is ever needed per-tournament (e.g. printed scorecards, accessibility), this token already exists and should be named/documented. Currently orphaned — no page uses it.

SHARPENED PRIORITY ORDER

Revised P1→P2 based on actual code state:

  1. P1 (real): Fix --font-mono in tokens.css → DM Mono first. Everything downstream depends on correct token value.
  2. P2 (real): Remove per-page inline :root light overrides from home, scorecard, scoreboard, admin, login, create. Dark theme cascades instantly.
  3. P3: Replace hardcoded green hex values in admin/scorecard with var(--green).
  4. P4+: Shared .ds-card, pill system, typography tightening — all as originally planned.
Grade adjustment: Token Coverage should move from B+ → A− (tokens.css is more complete than the §Review assessed). Design Parity stays D+ — the gap is real, just caused by override pattern not missing tokens.

§ Product Design Lens
Product Design Critique — Principal Designer Review · Claude Opus 4.8 · May 29, 2026
The §Review and §Second Opinion solve the implementation (token cascade, font-mono, override removal). This pass asks the prior question every designer must ask before touching a pixel: is the design itself right for who uses it and where? Several findings reframe the work rather than sharpen it.
FINDING 1 (High) — Context collapse: an admin-tool aesthetic is being cascaded onto a sunlit, gloved, one-handed consumer surface

The reference specimen — the bug-log popup — is an internal admin widget viewed indoors, on a desktop, by Rob. The plan cascades its dense, dark, mono language onto scorecard.html, which is used in the opposite context: outdoors, in direct sun, one-handed, by a golfer wearing a glove, often mid-round under time and social pressure. A design language should serve the consumer's context, not inherit from the internal tool it happened to be born in.

Stored strategic read confirms the underlying pattern (competitor-intel, 2026-05-21): "TOURney UX = admin-first… players get leaderboard." Propagating the admin aesthetic platform-wide risks hardening that admin-first bias into the design system itself.

ReframeOne token set, two surface tiers: Lean-back surfaces (marketing, platform, admin, login) — dark, dense, premium; the bug-popup aesthetic fits perfectly. Active surfaces (scorecard during a round, scoreboard at the turn) — high-contrast, large-tap, glanceable. Same gold, same fonts, same card grammar — different density & contrast budget per tier.
FINDING 2 (High) — Dark theme + outdoor sunlight is the single biggest unaddressed risk — and it needs Rob's decision

Dark UIs fail in direct sunlight. A mostly-black screen emits few photons even at max brightness, so screen reflections (sky, the player's own face) dominate and wash out legibility; light UIs push more light and stay readable. This is the most common real-world complaint for outdoor sports apps that adopted dark mode. The scorecard is the one screen guaranteed to be used in bright sun.

This is not "abandon dark." Dark is the brand and it is right for 6 of 8 surfaces. But the active-scoring surface needs a sunlight-survivable treatment. This is a genuine fork — surfacing it, not silently choosing (per DISAGREEMENTS rule):

  1. Course Mode toggle (recommended) — a high-contrast variant of the scoring surface only (near-white field or pure-black numerals on white), one toggle in the scorecard header, persisted per device.
  2. Keep dark, crank contrast + size — text #fff not #e8dcc8, score numerals ≥ 2.5rem, hit WCAG AA-large minimum. Cheaper, partial fix.
  3. Auto-switch by time-of-day or ambient-light sensor. Magical but fragile — ship after option 1.
FINDING 3 (Med) — A token table is not a design system. No principles are stated.

The ticket defines what (colors, fonts) but never the rules of use. Without principles, every future screen re-litigates the same decisions and drift returns within a sprint. Codify a short spine in the tokens.css header (or a DESIGN.md):

  1. Glance, don't read. A golfer checks the phone between shots — primary info must be legible in under one second.
  2. The score is the hero. On any scoring surface, the current score input is the largest, highest-contrast element. Nothing competes.
  3. Mono = data, never prose. DM Mono for numbers/labels; Barlow for sentences. (Already the instinct — make it law.)
  4. Gold is action & identity, not decoration. Reserve gold for interactive and brand moments so it stays meaningful.
  5. Earn every tap. Assume a gloved thumb in motion.
FINDING 4 (Med) — Touch ergonomics are unscoped, and golf is the hardest case

The plan ports the desktop admin widget's compact padding (0.75rem 1rem per row) onto a touch surface used one-handed, with a glove, sometimes while holding a club or bag. WCAG 2.5.5 and Apple HIG floor is 44×44pt; for gloved outdoor use the practical floor is 48–56px. Admin density on the scorecard will produce mis-taps on score entry — the single worst place to mis-tap, because it is the core action and the round is competitive.

SpecScore steppers ≥ 56px; all tappable controls ≥ 48px; ≥ 8px gap between adjacent targets. Compact density is permitted on the lean-back tier only.
FINDING 5 (Med) — The system must protect the primary action, not flatten it

The risk of applying dense dark cards everywhere: the scorecard becomes a uniform field of equal-weight cards, and the score stepper — the one thing the user came to do — loses prominence. The bug-popup reference has no single hero; every row is equal. That is correct for a log and wrong for a task surface. With Wolf / BBG / Quota / Snake / Skins / Nassau side-game panels now living on the scorecard (shipped 2026-05-27), the competition for attention is real and present.

Hierarchy law (scoring surfaces)Score input (hero) > hole context (par / yards / hole view) > navigation > format side-games. The design system should ship an explicit "hero" treatment — not just a flat .ds-card.
FINDING 6 (Low) — Motion, feedback & emotional design are missing from the system

TOURney already has a playful soul — HIO confetti, trash talk, the leaderboard score-flash in marketing.html. Scoring is an emotional, social act (birdies, blow-up holes, talking smack). The design-system ticket is purely static. The system should explicitly include feedback primitives:

  • Score-commit micro-feedback — subtle scale/flash on the score cell (the leaderboard flash already exists — reuse the motion token).
  • Birdie / eagle celebration — gold/blue color treatment already used in the marketing scorecard demo; promote it to a system token.
  • Haptic on submit — navigator.vibrate. Cheap, high delight, on-brand for a PWA.
Grade adjustment (product-design lens): Add the axis this ticket is missing — Fitness-for-Context: D. The system has not been evaluated against where and how it is used. "UX Consistency C+" is honest, but note that consistency to the wrong reference is not the win it appears to be — parity to an admin widget is not the goal; fitness to each surface's job is. Recommend re-scoping P1 of the §Plan from "make everything match the popup" to "establish the two-tier system, then make each tier match its job."
