Data Loading Priority Chain (scorecard.html lines 619–635)

Par and yardage are loaded through a three-tier override chain, highest priority last:

  1. settings table — pars_day* and yards_day* keys for tournament-specific overrides
  2. golf_courses table — gc.pars[] and gc.tees[].yards[] when round has a course_id (line 622–626)
  3. course_holes table — hole_number, par, yardage from tournament's linked courses row (lines 630–635) — final precedence

Hole image would naturally slot into this same chain. The course_holes table is the authoritative per-hole data source and is the right place to add image_url.

Strengths

  • Hole identity is unambiguous. currentHole (int 1–18) maps directly to array index — no lookup complexity.
  • renderHole() is the single render path. One function owns hole display. Image injection goes in exactly one place.
  • CSS framework in place. .hole-card and .hole-header are already scoped containers.
  • OSM + browser geo are free. Per platform memory: GPS + SVG hole view are available free via OpenStreetMap and browser geolocation — no satellite imagery cost.

§ Second Opinion
Independent Research Audit — Claude Sonnet 4.6 · May 29, 2026
Code + OSM + Mapbox API research. Three concrete implementation options the plan doesn't offer. Two structural corrections before execution starts.
CORRECTION — Migration missing lat/lng columns

The plan's P1 migration adds only image_url text. But Options B and C below both require hole coordinates. Without lat and lng on course_holes, satellite auto-generation and OSM lookup are impossible after the migration ships. Adding coordinates later means a second migration. Add all three columns in one shot:

ALTER TABLE course_holes
  ADD COLUMN image_url text,
  ADD COLUMN lat double precision,
  ADD COLUMN lng double precision;

Nullable, additive, zero risk. lat/lng can be populated by admin manually, by OSM lookup at course-add time, or by GPS tap-to-set in a future admin flow.

CORRECTION — Images belong on golf_courses library, not per-tournament

The plan routes hole images through course_holes (tournament-scoped). That means if Kokomo CC is used by 3 tournaments, Rob uploads 54 images. The golf_courses table is the platform-level course library — shared across all tenants. Hole images + coordinates should live there. Same fix as the data loading chain already uses: golf_courses → course_holes precedence. Concrete schema target:

-- library level (golf_courses): add hole_data jsonb
-- stores [{hole:1, lat:X, lng:Y, image_url:""}, ...] per course
ALTER TABLE golf_courses ADD COLUMN hole_data jsonb;

-- tournament override level (course_holes): keep image_url + lat/lng
-- only needed if tournament wants to override library data

scorecard.html already reads golf_courses at lines 622–626. Adding hole_data fits the existing precedence chain cleanly.

Option A — Mapbox Static Satellite (auto, no upload needed)

How it works: Given lat/lng for a hole, generate a static satellite URL on-the-fly. No storage, no upload, no admin work per hole.

// In renderHole() — satellite fallback when no image_url
function holeMapUrl(lat, lng) {
  const zoom = 17; // tight enough for one hole
  return `https://api.mapbox.com/styles/v1/mapbox/satellite-v9/static/`
       + `${lng},${lat},${zoom}/600x380@2x`
       + `?access_token=${MAPBOX_TOKEN}`;
}
  • Style: Must use satellite-v9 — Mapbox Standard Satellite is explicitly incompatible with Static Images API (confirmed in docs, planned for future release).
  • Free tier: 50,000 requests/month. 18 holes × N users per round — cache aggressively in the service worker. One fetch per hole per device per session at most.
  • Rate limit: 1,250 req/min — not a concern for this use case.
  • Token security: Public Mapbox tokens are visible in source. Mitigate with Mapbox URL restriction (restrict token to tourney.greenskeeper.studio in Mapbox dashboard). Or proxy through a Supabase Edge Function to keep token server-side.
  • Cache header: max-age=43200 (12h CDN). After first load, cached — no repeated billing per user.
  • Effort: ~20 lines JS + env var. Fastest path to real imagery.
Option B — OSM Overpass → Rendered SVG Diagram (free, offline-capable)

How it works: OSM has rich golf course geometry — every major US course is mapped with polygon features tagged by type and hole number. Query Overpass for golf=fairway, golf=green, golf=bunker, golf=tee, golf=water_hazard within the course bounds. Each feature is tagged ref=N (hole number). Render to SVG/Canvas — a clean schematic hole diagram, no satellite imagery needed.

// Overpass query — fetch all golf features for a course bbox
const query = `[out:json];
  (way[golf](${south},${west},${north},${east});
   relation[golf](${south},${west},${north},${east}););
  out geom;`;
fetch(`https://overpass-api.de/api/interpreter?data=${encodeURIComponent(query)}`)
  • Data quality: Excellent for well-known courses. Varies for small municipals. Can be checked before committing — query the course first, count ref-tagged features. If <10 holes mapped, fall back to Option A or placeholder.
  • Cost: $0 forever. OSM is open data.
  • Overpass reliability: Public endpoint is rate-limited and occasionally slow. Do NOT call Overpass from the client on every scorecard load. Correct approach: fetch once at course-add time (create wizard), store GeoJSON per hole in golf_courses.hole_data. Scorecard reads from Supabase — no Overpass at runtime.
  • Offline: GeoJSON stored in Supabase → service worker caches → works fully offline. Better than satellite (satellite images need network fetch per hole).
  • Effort: ~150 lines JS (Overpass fetch + GeoJSON→SVG projection). Higher up-front but zero ongoing cost and works offline natively.
Option C — Hybrid Fallback Chain (recommended)

Combine all three into one priority chain. renderHole() picks the best available source:

function renderHoleView(hole) {
  if (hole.image_url)          return renderImg(hole.image_url);      // 1. admin upload (highest quality)
  if (hole.lat && hole.lng)    return renderSatellite(hole.lat, hole.lng); // 2. Mapbox auto
  if (hole.osm_geojson)        return renderOsmDiagram(hole.osm_geojson);  // 3. OSM schematic
  return renderPlaceholderSvg(hole.par, hole.yards);                         // 4. par/yards schematic
}

This covers every state gracefully: new tournament with no data → placeholder; course in golf_courses library with lat/lng → satellite auto; OSM data pre-fetched → schematic diagram; admin uploaded custom photo → premium branded image. No state is ever blank.

Recommended execution order: Ship M1 with placeholder (as planned). Add lat/lng to migration. Wire Mapbox satellite as M1.5 (10 lines, instant payoff). Add OSM fetch-at-create-time in M2 alongside admin upload.

OSM Data Quality Check — Run Before Committing to Option B

Before building the OSM renderer, verify the target course is mapped. Paste this into overpass-turbo.eu with the course coordinates:

[out:json];
(way[golf](around:2000,{LAT},{LNG}););
out tags;

If results include 15–18 features with ref tags → course is well-mapped, Option B is viable. If <5 results or no ref tags → skip to Option A (satellite).

Priority recommendation: Add lat/lng to migration now (free). Ship M1 with placeholder as planned. Wire Mapbox satellite as a 20-line add-on (instant real imagery, no admin work). Build OSM fetch-at-create-time in M2 for offline diagram support. Admin upload remains as premium override for branded content.

§ Product Design Lens
Product Design Critique — What Is the Golfer Actually Trying to Do? · Claude Opus 4.8 · May 29, 2026
The §Review and §Second Opinion debate how to source a hole image — upload vs. Mapbox satellite vs. OSM. This pass asks the prior question: during scoring, what does the golfer need to see — and is a satellite photo it? The answer flips the priority order and resolves a live conflict with a stored product decision.
FINDING 1 (High) — The job is mis-framed. This isn't "show a hole image" — it's "orient a stranger on a hole they've never played."

Stored core demo insight (competitor-intel, 2026-05-21): "TOURney's primary demo use case = groups going to courses they've NEVER played. GPS + hole views are the experience differentiator for new-course trips, not a luxury." That reframes the entire feature. The artifact must answer the golfer's real questions standing on the tee of an unknown hole:

  • Which way does the hole go? (dogleg, blind, straight)
  • What do I have to carry? (water, bunker, waste)
  • Where is the trouble, and where is safe?
  • Where is the green, and how far am I?

"Show a picture of the hole" satisfies none of these reliably. "Orient me on this hole" is the actual job. Everything below follows from that distinction.

FINDING 2 (High) — Satellite imagery is the wrong primary — and it contradicts a stored product decision

Product problem: a Mapbox satellite tile is decorative, not directive. Every hole renders as a similar dark-green blob; aerials are frequently years stale and the wrong season; the tile is north-up, so it rarely matches the direction of play and the golfer must mentally rotate it; and on a phone in bright sun it collapses to a muddy rectangle. It demos well and helps the player very little.

Conflict: the stored memory decision states plainly — "never use satellite imagery for hole cards" (project_tourney_core_demo_insight) — yet this ticket's §Second Opinion makes Mapbox Static Satellite the M1.5 centerpiece. Note the source tension: the same 2026-05-21 competitor-intel drawer says "satellite — REVISED: BUILD FREE." These two stored facts disagree. Logged to DISAGREEMENTS.md for Rob to resolve — not silently chosen.

Design verdictA schematic SVG, oriented tee → green, is the right primary: sun-legible, consistent hole-to-hole, branded to TOURney's tokens, offline-native, and it actually communicates the hole. Satellite, if kept at all, is an optional "aerial" toggle — never the default. This aligns the build with the stored decision.
FINDING 3 (High) — The most valuable layer is missing from both the plan and the second opinion: "you are here"

The competitor gap analysis and the core demo insight both point at GPS. A hole diagram without the player's live position is a static picture; a diagram with a GPS dot and a live yardage-to-green number is a genuine playing aid — the exact thing that makes a stranger comfortable on a course they've never played. The lat/lng schema work is the enabler; the product payoff is the dot and the distance, not the basemap underneath it.

Design the view as a layered playing aid, not an image slot Layer 0 — par + yardage (always, instant, zero network).
Layer 1 — schematic shape tee → green with hazard glyphs (the hero).
Layer 2 — GPS "you are here" dot + live distance-to-green (the differentiator).
Layer 3 — optional aerial photo toggle for those who want it.
This also future-proofs cleanly toward the P1 player-scoring + GPS roadmap already on file.
FINDING 4 (Med) — Interaction model: when does the view appear, and does it fight the score stepper?

The plan inserts #holeView between .hole-header and .hole-nav with a vague "collapsible." But timing is the design question. A golfer wants the hole view on arrival at the tee (planning the shot) and wants it out of the way while entering a score. Those are opposite states and the UI should switch between them automatically.

State designOn hole change → view auto-expands (you just walked to a new tee — orient me). On score-stepper focus → view auto-collapses to a slim par-colored strip (now I'm recording — get out of the way). Manual tap overrides; state persists per hole in sessionStorage (the plan already gestures at this). Net: the view shows up exactly when wanted and protects the primary action when not.
FINDING 5 (Med) — The SVG "placeholder" is designed as a consolation prize. It is actually the product.

The plan frames the SVG as the fallback "when nothing better exists" — a gray box reading "Par 4." But per Findings 1–3 the schematic is the best artifact for the job, not the worst. It is also the only layer that works today for the 90 existing flat golf_courses rows, which have par/yards arrays but no coordinates. Investing in a real schematic ships value to every existing tenant on day one; investing in satellite ships value only after someone populates lat/lng.

ElevateRename "placeholder" → "hole schematic." Give it tee and green markers, a fairway path, simple hazard glyphs, orientation to the direction of play, and a par-color accent. Make it the M1 hero; treat photo and aerial as later enhancements.
FINDING 6 (Low) — The hole view inherits the unresolved theme question from the sister ticket

A satellite photo (bright, full-color, north-up) dropped into a dark-card scorecard reads as a foreign object — and if the scorecard adopts a high-contrast "Course Mode" for sunlight (see the UX Design System ticket, Finding 2), a dark satellite tile becomes nearly invisible. A schematic SVG drawn from TOURney's own tokens adapts to whichever theme wins. One more reason schematic > photo. These two tickets must be decided together, not in isolation.

FINDING 7 (Low) — Accessibility & data honesty
  • Alt text must describe the hole — "Hole 7, par 4, dogleg right, 410 yd" — not "Hole 7 satellite."
  • Graceful GPS degradation — if location is denied or unavailable, fall straight back to the schematic. Never leave a dead "locating…" state on screen mid-round.
  • No false precision — never render a confident pin on an approximate lat/lng. A playing aid that lies about distance erodes trust fast. Mark estimated positions, or omit the distance until the fix is good.
Revised recommendation — flip the priority order: M1 = schematic SVG hole view as the hero (works for all 90 courses today, sun-legible, offline, on-brand). M2 = GPS "you are here" + distance-to-green (the real differentiator; aligns with the P1 scoring + GPS roadmap). M3 = optional admin photo upload (premium override) and an optional aerial toggle. Demote satellite from "M1.5 centerpiece" to "optional aerial layer," consistent with the stored product decision. Net effect: less API dependency, lower cost, better job-fit, and no contradiction with memory.

let gpsWatch = null;
function startHoleGps(holeData) {
  if (gpsWatch != null) navigator.geolocation.clearWatch(gpsWatch);
  if (!holeData || !holeData.green || !navigator.geolocation) return;
  gpsWatch = navigator.geolocation.watchPosition(pos => {

  }, () => {/* denied — silent, schematic stands */}, { enableHighAccuracy:true, maximumAge:5000 });
}
function haversineYards(a, b) {
  const R=6371000, toR=x=>x*Math.PI/180;
  const dLat=toR(b.lat-a.latitude), dLng=toR(b.lng-a.longitude);
  const s=Math.sin(dLat/2)**2 + Math.cos(toR(a.latitude))*Math.cos(toR(b.lat))*Math.sin(dLng/2)**2;
  return 2*R*Math.asin(Math.sqrt(s))*1.09361; // m → yd
}
