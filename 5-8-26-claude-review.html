What TOURney Is

TOURney is a multi-tenant golf tournament SaaS PWA. Each tenant gets a white-labeled tournament site at /t/:slug/ with a home page, live scoreboard, per-player scorecard, social feed, player directory, and champion history. The platform layer (marketing, /create wizard, /platform ops hub) is shared. Bova Invitational is the v1 live tenant. The architecture is Supabase-backed vanilla JS MPA hosted on Vercel — no framework, no build step, deploy on git push.

§2 — Forward Vision
Council of Five
Five highest-leverage improvements grounded in current platform state. Each extends what already exists — no from-scratch builds.
1
UX / Delight
Loading Skeletons — Kill the Blank Flash
Every tournament page does an async Supabase fetch before rendering. Until the response arrives, the page is blank. On slow connections or first paint, this looks broken. SW v17 handles caching correctly but the blank window before data loads is the #1 perceived-performance issue across all pages.
Build plan: Add .skeleton CSS class (pulse animation, gold shimmer). In each page's HTML, add skeleton placeholder elements inside the main containers. In the fetch callback, swap .skeleton for real content. tourney-init.js can expose a window.tourney.loading boolean. ~2 hours across all pages.
2
Scale / Architecture
Tournament Series — One Brand, Many Events
Right now every tournament is standalone. The Bova group will want Bova Invitational 2026, 2027, 2028 — same brand, same players, year-over-year history. No schema or UX exists for this yet. A series_id on the tournaments table unlocks all-time leaderboards, carry-forward handicaps (carry_forward_enabled already exists in migrations), and a single brand landing page.
Build plan: Migration 012 — add series_id UUID REFERENCES series(id) to tournaments. New table: series(id, slug, name, owner_email). Add /s/:slug route → series.html showing all events. Wire carry_forward_enabled flag to actually pull prior-year scores into handicap calculation. 1 migration + 1 new page.
3
Business
ToS + Privacy Auto-Gate on /create
Stripe can't go live without legal pages. The /create wizard step 1 (identity) should have a checkbox: "I agree to the Terms of Service and Privacy Policy." These pages don't exist yet. This is a blocker for the LLC → payment activation path — you can form the LLC this week and still be blocked on payments if these aren't ready when the entity is.
Build plan: Create tos.html and privacy.html (static, minimal legal boilerplate appropriate for pre-revenue SaaS). Add /tos and /privacy Vercel rewrites. Add checkbox to create.html step 1 with links. Gate the Next button on checkbox. ~3 hours total including legal text.
4
Infrastructure
CI on Push — Run test.js Automatically
test.js already exists and runs against the live DB. It's currently run manually. A GitHub Actions workflow that runs node test.js on every push to main would catch regressions before they reach production. The test suite already flags false positives gracefully — 0 failures with 3 known warnings is the clean baseline.
Build plan: Create .github/workflows/ci.yml — on: push: branches: [main], checkout, node 20, npm install, set SUPABASE env vars as GitHub secrets, node test.js. Add exit code check (currently test.js may not exit non-zero on failure — verify and fix). ~1 hour.
5
Data / Feature
Handicap-Adjusted Net Score on Scoreboard
player.html already shows handicap tier and calculates rolling average after 5+ rounds (from the scores table). The scoreboard shows gross totals. A "Net" toggle that subtracts handicap from gross score would make competitive play meaningful for mixed-handicap groups — exactly the Bova use case. tournament_mode + hdrTotal toggle already exists in the scoreboard JS.
Build plan: Add handicap column read to scoreboard.html player query (already in players table). In renderRows(), compute net = gross - handicap. Add a Net/Gross toggle button alongside the existing mode badge. Wire to existing hdrTotal element. No migration needed. ~2 hours.

§5 — Security Analysis
Security Review
Current grade: B- (improved from D+ on May 6 via migrations 006–011 and Vercel header hardening). Open critical: 2 edge functions with zero auth still live in production.
Methodology

Inspected all 11 migration files (migrations/001–011) for RLS policy text and USING clauses. Read all 5 edge functions (supabase/functions/*/index.ts) for auth patterns. Grepped innerHTML across all .html and .js files to find XSS surfaces. Grepped for function esc to verify escaping coverage. Read vercel.json for Content-Security-Policy header. Cross-referenced findings against the SECURITY_PLAN.md doc (generated May 7, 2026) and the May 7 diary entry confirming migrations 006–011 applied to live DB. Compared current code state against prior B- grade to assess change.

HIGH send-push — Zero Auth in Live Production Function
The committed version of supabase/functions/send-push/index.ts adds JWT verification. However, the live Supabase function has NOT been redeployed since this fix was committed — SUPABASE_ACCESS_TOKEN was not available in the session that wrote the fix. The currently-live edge function accepts any unauthenticated POST containing a valid tournament_id UUID and broadcasts a push notification to all tournament subscribers. Impact: free spam vector to all registered players. As send-push gains more event types (match updates, score alerts), this surface expands.
Fix Plan 1. Set SUPABASE_ACCESS_TOKEN env var (from Supabase dashboard → Settings → Access Tokens).
2. Run: npx supabase functions deploy send-push --project-ref jllugkiojeoopitdvzsa
3. Verify deployment in Supabase dashboard → Edge Functions → send-push → Logs.
4. Test: send a POST without Authorization header — expect 401 response.
HIGH send-install-email — Zero Auth, No Fix Committed
Unlike send-push (which has a committed fix), supabase/functions/send-install-email/index.ts has no authentication check and no fix is committed. The function accepts any POST with email + tournament_id and triggers a Resend email. There is no rate limit at the function level. An attacker knowing a tournament_id UUID can send unlimited emails to arbitrary addresses using Greenskeeper Studios' Resend account, risking Resend account suspension and domain reputation damage.
Fix Plan 1. Add JWT auth check: const authHeader = req.headers.get('Authorization'); if (!authHeader?.startsWith('Bearer ')) return new Response('Unauthorized', {'{'}status: 401{'}'});
2. Verify token with Supabase client: extract user, confirm email matches param.
3. Add Resend rate limit: max 1 email per email+tournament_id per hour (check via DB or KV).
4. Deploy: npx supabase functions deploy send-install-email --project-ref jllugkiojeoopitdvzsa
MEDIUM Content-Security-Policy — unsafe-inline Nullifies Script Protection
The Content-Security-Policy header in vercel.json includes unsafe-inline in the script-src directive. This means any XSS payload that injects a <script> tag inline executes freely — the CSP provides no protection against the XSS surfaces that remain open (admin.html, feed.html). Without unsafe-inline, a browser would block inline script injection even if the esc() wrapper was bypassed.
Fix Plan 1. Audit all inline <script> blocks across .html files — extract to separate .js files.
2. Remove unsafe-inline from CSP script-src in vercel.json.
3. Use nonces (script-src 'nonce-{'{'}value{'}'}' ...) for any inline scripts that can't be extracted (Vercel Edge Middleware can inject nonces per request).
4. Test: load each page, check browser console for CSP violation errors, fix each one.
MEDIUM admin.html — URL Strings in innerHTML Without esc()
Two locations in admin.html (approximately lines 2044 and 2194) render URL strings into innerHTML without wrapping in esc(). Confirmed in the May 7 security review. While these URLs likely come from settings (admin-controlled), a compromised admin or a malicious settings write could inject HTML via a crafted URL string. The fix is trivial — both are template literals missing an esc() wrapper.
Fix Plan 1. Open admin.html, search for innerHTML near lines 2044 and 2194.
2. Wrap the URL variable in esc(): change ${'{'}url{'}'} to ${'{'}esc(url){'}'}.
3. Grep for any remaining innerHTML assignments not using esc() — the SECURITY_PLAN.md lists the complete grep output as the source of truth.
MEDIUM feed.html:377 — _parseMentions Flows Through innerHTML
feed.html:377 implements _parseMentions(str) by setting d.innerHTML = str then calling d.innerHTML.replace() to wrap @mentions. The input string str is the post message content — user-generated text from the feed. If the input contains HTML tags, they execute before the @mention replacement runs. The esc() helper exists in feed.html (line 658) but is not applied to str before it enters d.innerHTML.
Fix Plan 1. In _parseMentions, change the first line from d.innerHTML = str to d.innerHTML = esc(str).
2. Verify the @mention regex still matches after HTML escaping (it targets @Name patterns — should be unaffected by entity encoding of special chars).
3. Regression test: post a message containing <b>bold</b> — verify it renders as literal text in the feed.
INFO player_accounts — Anon Read Exposes billing_status
Migration 005 (005_invitations_and_accounts.sql) includes policy "anon read player_accounts" with USING (true). Any unauthenticated visitor can query the player_accounts table and read all billing_status values. While billing_status (active/comped/trial) isn't a financial secret, it reveals which users have paid accounts — useful for targeted social engineering. Low urgency pre-launch, but should be tightened to auth.uid() = user_id before going live with real billing data.
Fix Plan 1. Create migration 012: DROP POLICY "anon read player_accounts" ON player_accounts;
2. CREATE POLICY "own read player_accounts" ON player_accounts FOR SELECT TO authenticated USING (auth.uid() = user_id);
3. Verify no public-facing pages depend on anon reads of player_accounts (check scoreboard.html, home.html).
✓ Security Positives
  • stripe-webhook — constructEventAsync(body, sig, webhookSecret) verifies Stripe signature before processing any event. Correct implementation.
  • create-checkout — JWT-gated, validates tournament ownership via owner_email = auth.email() before creating session. Tournament must be in pending_payment status — prevents double-charging.
  • esc() helper — defined in feed.html (line 658) and used consistently for player names throughout. Player-entered data (first_name, last_name, trash_talk in feed) is escaped.
  • Vercel headers — HSTS (max-age=31536000), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin all correctly configured in vercel.json.
  • is_admin retired — migration 006 dropped the column. All admin checks now go through tournament_admins email lookup — scoped per tournament.
  • Migrations 008–011 — players, scores, push_subscriptions, trash_talk all received RLS tightening. The security posture improved substantially from D+ (May 6) to B- (May 7) in a single session.
