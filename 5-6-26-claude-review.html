🏌️ What TOURney Is

TOURney is a multi-tenant golf tournament platform built for private events (scrambles, stroke play, best-ball, shambles, etc.). Each tournament gets its own branded URL (/t/{slug}/), live scoreboard, scorecard entry, player profiles, activity feed, and admin control panel.


The platform layer (tourney.greenskeeper.studio) handles marketing, 5-step tournament creation wizard, and a super-admin panel (Rob only). The tournament layer (/t/{slug}/) is the per-event app — every tournament can be themed (logo, colors, hero photo) and configured (rounds, formats, registration settings) entirely from the admin UI without touching code.

✅ Strengths
  • Zero-dependency client. No build step. Ships static. Deploy = git push to Vercel.
  • Multi-tenant tenancy fully wired. tournament_id FK + composite PK on settings. Five migrations applied.
  • Email-based tournament_admins + RLS settings policy already done (migration 003+004). Settings writes are RLS-gated.
  • Stripe infrastructure pre-staged: edge functions create-checkout + stripe-webhook live, tournaments.stripe_* columns + player_accounts.billing_status done.
  • Realtime scoreboard via Supabase channels. No polling.
  • PWA: SW tourney-v16, offline score queue, push notifications, network-first HTML.
  • Every render path uses an esc() helper for player names/team names. XSS-conscious in most files.
  • Active QA discipline — 12 tracked sessions, named commits, regression notes.
  • Local localStorage namespaced by slug. No cross-tournament bleed.
  • 5-step creation wizard handles auth → billing-gate → DB seed → admin redirect end-to-end.
⚠️ Gaps & Real Bugs
  • CRITICAL — player_accounts RLS wide open. Policy: auth manage player_accounts FOR ALL TO authenticated USING (true) WITH CHECK (true). Any signed-in user can UPDATE any row, set billing_status='comped', bypass Stripe entirely. Bypasses your monetization.
  • CRITICAL — invitations RLS open to anon. anon update own invitation has no email/id filter. Any anon user can UPDATE any invitation. Forgery / status flip possible.
  • XSS in admin.html. Lines 1169 + 1709: ${p.trash_talk} and ${p.why_me} rendered to innerHTML without esc(). Both are player-controlled at registration. A malicious player → script in admin's session.
  • Dual admin source-of-truth. players.is_admin still written (admin.html:1193, 1845, create.html:771) AND tournament_admins table is canonical for RLS. Drift hazard — UI gates can pass while RLS rejects, or vice-versa.
  • platform.html gate is client-only. PLATFORM_EMAIL equality check at line 164. Bypassable in DevTools — but RLS protects DELETE so worst case is reading the dashboard view.
  • No CSP header. vercel.json has cache-control only. Adding Content-Security-Policy would harden against the XSS path above.
  • Bova formats unverified. Day1/Day2/Day3 = stroke/scramble/best_ball seeded by guess. Chris Bova has not confirmed.
  • No live test scores. Leaderboard/scorecard rendering never exercised end-to-end with realistic data.
  • HTML files heavy: admin.html 151KB, scorecard.html 87KB, home.html 144KB.
  • No error monitoring (Sentry) — production JS exceptions are invisible.
  • No analytics — funnel drop-off in /create wizard is unknown.
  • Round naming hardcoded day1/day2/day3 — known limitation flagged in PHASE2_PLAN.

Council of Ideas — What's Next for Polish
Five engineers around the table. Five ideas to make TOURney feel genuinely professional. Ranked by impact-to-effort ratio.
1
UX · High Impact
Extend Email Beyond /install — Welcome, Round Open, Results Recap
The send-install-email edge function already exists, so the email pipeline is half-built. Extend it. Today only one transactional email goes out (PWA install). Players get nothing on registration confirm, nothing when a round opens, nothing when the tournament ends. Add three more templates triggered on database events: Welcome (after RSVP confirm), Round Open (when admin flips round_state), Final Recap (at tournament_end with leaderboard + standout scores). The recap email is the viral moment — it lands in the group chat the night the tournament ends.
Build: Generalize send-install-email into a send-email edge function with template parameter. Add Postgres triggers (or invoke from admin actions) to fire each template. Ship before Bova 2026.
2
Data · High Impact
Live Score Feed with Animations on Scoreboard
The scoreboard has Supabase Realtime wired up — but there's no visual reaction when a score comes in. No row highlight, no rank-change animation, no "just submitted" indicator. A score drops and the board silently re-sorts. That's a missed moment. When someone eagles hole 7 and the leaderboard reshuffles with a subtle animation and a "🦅 Eagle — Team A" toast, everyone in the cart looks up.
Build: Track previous rank per team in JS. On Realtime update, CSS transition the row, fire a toast for birdie/eagle/hole-in-one events. ~1 day of work, massive perceived quality lift.
3
Polish · Medium Impact
Onboarding Checklist in Admin Dashboard
A new tournament owner finishes the creation wizard and lands in admin.html staring at a dense UI. There's no "you're 70% set up — here's what's left" moment. An onboarding checklist (Add your logo → Set your course → Open registration → Add players → Open scoring) would make the product feel finished and guide owners to the aha moment faster. Right now they have to figure it out themselves.
Build: Read settings from Supabase, render a sticky progress bar or collapsible checklist at the top of admin. Each item links to the relevant admin tab. Pure front-end, no schema changes. ~4 hours.
4
Business · Medium Impact
Post-Tournament Recap Page (Auto-Generated)
After a tournament ends, there's no canonical "here's what happened" artifact. The champions.html hall of fame is a static list. What if closing a tournament auto-generated a recap page with the final leaderboard, team highlights, round-by-round progression, best scores, and a shareable link? This becomes marketing — organizers share it on social, and it's the best possible ad for TOURney because it shows the product doing real work.
Build: New recap.html page, same pattern as other pages. Tournament recap is read-only — just queries scores/players. Could be a shareable static URL with no login required. Screenshots automatically become social posts.
5
Infrastructure · High Leverage
Error Monitoring + Lightweight Analytics (Sentry / Posthog)
You're flying blind in production. If a player's scorecard crashes on hole 12, you don't know until they text you. If 40% of people drop off on step 3 of the creation wizard, you have no data. Sentry (free tier) catches unhandled JS exceptions with stack traces and the Supabase query that triggered them. Posthog (free tier, self-hostable) tracks page views, funnel conversion, and feature usage — all without violating GDPR if configured correctly. This is the difference between building on feelings and building on facts.
Build: Drop a Sentry CDN snippet into tourney-init.js (one line). Add Posthog pageview tracking. Both are free, both are 30-minute setups, both pay dividends on every future feature decision. Do this before Bova 2026 runs — you want data from the live event.

Section 5 of 5
Security Review
Full threat model. Every finding rated by severity. Fix plan included for each. Address CRITICAL before opening to paying customers.

Methodology: read every migration SQL, grep'd innerHTML usage with surrounding esc() calls, audited RLS policies in the five applied migrations, and traced the billing_status trust path from create.html → player_accounts → Stripe webhook. Findings below are evidence-based, not theoretical.

🔴 CRITICALplayer_accounts RLS Bypasses the Stripe Billing Gate
This is the most expensive bug in the codebase. Migration 005_invitations_and_accounts.sql defines:
CREATE POLICY "auth manage player_accounts" ON player_accounts FOR ALL TO authenticated USING (true) WITH CHECK (true); Any signed-in user can UPDATE player_accounts SET billing_status='comped' WHERE email='attacker@example.com'. The create.html billing gate at line ~145 checks billing_status against BILLING_OK = {'active','comped','trial'}. Self-comp = unlimited free tournament creation. The Stripe webhook is never invoked. Your monetization is bypassable in three lines of JS in DevTools.
Fix Plan — Same Day
  1. Drop the open policy. Replace: SELECT — own row only (email = auth.email()). UPDATE/INSERT — service_role only (Stripe webhook).
  2. Stripe webhook edge function already runs as service_role via SUPABASE_SERVICE_ROLE_KEY env var — bypasses RLS by design. No change there.
  3. For Rob's manual comp grants in platform.html, route through a new grant-comp edge function (gated by email check on auth.jwt()) instead of direct upsert.
  4. Migration 006_lock_player_accounts_rls.sql — file the SQL.
🔴 CRITICALinvitations RLS — Anonymous UPDATE on Any Row
Same migration:
CREATE POLICY "anon update own invitation" ON invitations FOR UPDATE TO anon USING (true) WITH CHECK (true); Policy name claims "own invitation" but predicate is true — no email = ... filter, no id = ... match. Any anonymous user can flip any invitation's status to accepted or declined. They can also change the email field on someone else's invitation to redirect it to themselves.
Fix Plan — Same Day
  1. Replace anon-write policy with single-purpose accept-invitation edge function. Function takes {invitation_id, token}, validates a per-invitation token (add access_token column), updates status as service_role.
  2. Or: drop UPDATE policy entirely. Use Postgres function with SECURITY DEFINER + token validation.
  3. UNIQUE constraint on (tournament_id, email) already exists. No structural change.
🔴 HIGHXSS — admin.html Renders trash_talk + why_me Without esc()
admin.html:1169 and admin.html:1709:
<td ...>${p.trash_talk || '—'}</td> Both trash_talk and why_me are player-controlled at registration via the home.html RSVP form. Rendered into a template literal assigned to player table's innerHTML. No esc() wrapper. A malicious registrant submits <img src=x onerror="..."> as their trash talk. When Rob (or any tournament admin) opens the player tab, the script runs in admin's authenticated session — they can write any settings, grant any admin, drop any score row that admin's RLS allows.
Note: Most other render paths use esc() (verified in feed.html, scoreboard.html, directory.html, profile.html, scorecard.html, champions.html, platform.html, player.html). admin.html is the outlier — defines its own esc() at line 1722 but doesn't apply it to these two fields.
Fix Plan — 30 minutes
  1. Wrap both renders: ${esc(p.trash_talk || '—')} and ${esc(p.why_me || '')}.
  2. Grep admin.html for every ${p\. pattern in template literals — verify each is wrapped in esc(). Same for any innerHTML assignment that interpolates DB data.
  3. Add CSP header (see #6 below) as defense-in-depth.
🟠 MEDIUMDual Admin Source-of-Truth — players.is_admin + tournament_admins
Migration 003 + 004 made tournament_admins the canonical admin model for RLS — settings writes are gated on tournament_admins.email = auth.email(). But players.is_admin still exists and is still being written to in five places (admin.html lines 1193, 1845, 1856; create.html line 771; champions.html, course.html, directory.html still gate UI on players.is_admin in some flows).
Risk is drift: a tournament_admins row gets created without setting players.is_admin (or vice-versa). UI passes the gate but RLS rejects, or RLS passes but UI hides controls. Mixed-system bugs ship to production and only surface during a live tournament under load.
Fix Plan — 2 hours
  1. Pick one source. Recommend tournament_admins — already wired into RLS, already email-based.
  2. Replace every players.is_admin read with a join: EXISTS (SELECT 1 FROM tournament_admins WHERE tournament_id = ? AND email = ?) — or expose via RPC.
  3. Migration 007_drop_players_is_admin.sql: ALTER TABLE players DROP COLUMN is_admin; after all reads/writes converted.
🟠 MEDIUMtrash_talk Table — Anonymous INSERT, No Rate Limit
feed.html documents the policy: CREATE POLICY "public insert" ON trash_talk FOR INSERT WITH CHECK (true). Any anon user can post any number of messages to any tournament. Combined with no rate limiting at the Supabase API layer, a bot could flood the feed with thousands of posts. Less severe than RLS issues above (no privilege escalation), but ugly — and spam content lands on every player's screen via realtime.
Fix Plan
  1. Tighten policy: require auth — FOR INSERT TO authenticated WITH CHECK (player_id = auth.uid()).
  2. Add Postgres trigger: reject if same player_id posted within last 10 seconds.
  3. Add admin "delete post" UI in admin.html so spam can be wiped fast during a live event.
🟠 MEDIUMNo Content-Security-Policy Header
vercel.json sets only Cache-Control. No CSP, no X-Frame-Options, no Referrer-Policy. CSP is the second line of defense against the XSS issue above — even if a script gets injected, CSP can prevent outbound network calls or inline execution.
Fix Plan — 15 minutes Add to vercel.json:
"headers": [{ "source": "/(.*)", "headers": [ { "key": "Content-Security-Policy", "value": "default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net https://*.supabase.co; connect-src 'self' https://*.supabase.co wss://*.supabase.co; img-src 'self' data: https:; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com;" }, { "key": "X-Frame-Options", "value": "DENY" }, { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" } ] }] 'unsafe-inline' stays for now (every page uses inline scripts). Remove long-term by extracting to external .js files.
🟢 LOWplatform.html Gate Is Client-Only
platform.html:153 hardcodes PLATFORM_EMAIL = 'robert.t.madsen13@gmail.com' and gates UI access on email !== PLATFORM_EMAIL at line 164. Bypassable via DevTools. However, destructive ops are RLS-protected: tournaments DELETE policy requires auth.email() = owner_email, so a bypasser can only see the dashboard view, not delete other people's tournaments. BUT — the compEmail grant flow (line 296) writes to player_accounts directly. Combined with the player_accounts RLS hole above, anyone who bypasses the UI can grant comp status to anyone. That's why the player_accounts fix is critical.
Fix Plan Once player_accounts writes go through the new grant-comp edge function (Critical #1), platform.html gate becomes purely UX. Add an RLS policy on player_accounts UPDATE that checks auth.email() = 'robert.t.madsen13@gmail.com' as backup defense.
🟢 LOWScore Submission — UNIQUE Constraint Already Present
SETUP.md defines UNIQUE (player_id, round, hole) on the scores table. Combined with scorecard.html:1858 using upsert with onConflict: 'player_id,round,hole', score writes are idempotent — a flood of duplicate submissions can't corrupt the leaderboard. Good.
What's missing: rate limiting at the API layer. A malicious player with auth could write valid different scores rapidly to game realtime updates. Low impact for a private-tournament product.
Fix Plan Optional. Add Supabase rate-limit (Pro plan) or Postgres trigger that throttles per-player write rate. Defer until real abuse case appears.
ℹ️ INFOSupabase Publishable Key in Client — By Design
