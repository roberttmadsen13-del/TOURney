Current State Audit
What tier infrastructure exists today, what's gated, what's missing, and what the DB already supports.
Existing Tier Gate Infrastructure

A tier gate system exists but is minimal. Key files and line citations:

  • lib/tier-config.js — defines TOURNEY_PLANS with 4 plans: free | pro | scratch | comped. Features gated: design and access only. Free plan has both set to false.
  • admin.html:986 — applyTierGates(plan) iterates 2 tabs: lockDesign (Setup tab) and lockAccess (Access tab). Locks UI elements and adds .locked class to tab buttons when canAccess(plan, feature) returns false.
  • admin.html:890 — PLATFORM_OWNER = 'robert.t.madsen13@gmail.com'. Platform owner always gets 'scratch' plan (all features unlocked).
  • admin.html:964 — On login, reads player_accounts.plan for the authenticated email. Falls back to 'free' if no row. Passes plan into applyTierGates().
  • admin.html:981 — checkSession() path also calls applyTierGates() on session restore.
  • admin.html:309–314 — Upgrade modal exists: #upgradeModal with link to /player-upgrade. Text: "available on TOURney Pro plan." Already wired.

Gap: No player count, round count, or team count is currently gated. applyTierGates() only locks 2 UI tabs. Adding players, rounds, or teams is unrestricted on the free plan.

player_accounts Table State
  • Migration 005 (005_invitations_and_accounts.sql) — created player_accounts with columns: email TEXT PK, plan TEXT DEFAULT 'free' (free / player / pro), billing_status TEXT DEFAULT 'inactive' (active / inactive / cancelled / trial), stripe_customer_id TEXT, created_at, updated_at.
  • Migration 008 (008_security_rls_hardening.sql:67) — replaced the original USING(true) blanket policies. Now: owner reads own row only (auth.email() = email). Service role used for webhook writes.
  • Migration 012 (012_restrict_player_accounts_anon_read.sql) — dropped the anon-read USING(true) policy that was exposing plan and billing_status to all anonymous visitors. Fixed.
  • Migration 002 (002_add_billing.sql) — added stripe_subscription_id to tournaments table (not player_accounts). Tournament-level billing exists but is separate from account-level plan.

The table supports plan gating today. plan column is the source of truth for applyTierGates(). The stripe-webhook edge function handles customer.subscription.created/updated and writes plan + billing_status back to this table.

Stripe Edge Function Inventory
  • supabase/functions/create-checkout/index.ts — creates a Stripe Checkout session. Already accepts tier in request body and stores it in subscription metadata. Validates tier in PRICE_IDS server-side.
  • supabase/functions/stripe-webhook/index.ts — handles checkout.session.completed, customer.subscription.updated, customer.subscription.deleted, invoice.payment_failed. Extracts metadata.tier and upserts player_accounts.plan = tier, billing_status = 'active'.
  • supabase/functions/create-player-checkout/index.ts — separate player-level checkout (distinct from admin/tournament checkout).
  • supabase/functions/create-donation-checkout/index.ts — donation flow, not relevant to tier gating.

The Stripe infrastructure is substantially built per the 5-11-26 runbook (Phase 8). The missing piece is enforcement: applyTierGates() does not yet check player count, round count, or team count against plan limits.

Current Hard Limits on Players / Rounds / Teams
  • Players: admin.html:2392 — maxPlayers = parseInt(dsMaxPlayers.value) || 24. Default is 24 but admin can set any value. No plan-based enforcement. create.html:372 also defaults to maxPlayers: 24 with UI buttons for selection.
  • Rounds: migrations/007_round_model.sql — rounds table supports 1–6 rounds (loop iterates i IN 1..6). No plan-based cap on rounds. Admin can add rounds freely.
  • Teams: admin.html:938 — TEAM_LETTERS = ['A','B','C','D','E','F','G','H'] (8-team max hardcoded). _teamCount starts at 2. Team names stored in settings table as team_a_name, team_b_name, etc. No plan gate on team count.
  • Team colors/images: No team_*_color or team_*_image columns/settings keys exist anywhere in migrations or admin.html. This feature is entirely absent from the current data model.
  • Captain assignment: Legacy worktree (.claude/worktrees/admiring-kirch-5445a8) has challengers_captain in settings and team_assignments JSON. Current main-branch admin.html uses teamAssignments keyed by player ID to team letter — no captain concept. Captains are not currently assignable in production.

Strategic Plan
Tier design, Stripe integration, captain model, and team customization storage — ordered by dependency and revenue impact.
Strategic Priorities (P1 → P5)
  1. P1 — Define Free vs. Pro limits in tier-config.js. Add maxPlayers, maxRounds, maxTeams to each plan. Free: 24 players, 3 rounds, 4 teams. Pro: 120 players, 10 rounds, 16 teams (effectively unlimited for most events). This is the single source of truth for all gate enforcement — do this first, everything else depends on it.
  2. P2 — Enforce limits in admin.html applyTierGates(). Check counts before adding a player, before adding a round, and before increasing team count. Trigger openUpgradeModal() when limit hit. This is the revenue gate — it directly converts free users.
  3. P3 — Wire Stripe Checkout for Pro upgrade in admin.html. The /player-upgrade link in the existing upgrade modal should call create-checkout edge function with tier: 'pro'. Verify full loop: checkout → webhook → player_accounts.plan → page reload refreshes gates. Use Stripe test mode first.
  4. P4 — Add captain assignment UI in admin.html team panel. Each team column needs a "Set Captain" control that writes team_a_captain_id (player UUID) to settings. The settings pattern is already used for team_a_name — extend it. Downstream: home.html and directory.html read captain for display.
  5. P5 — Add team color and image to settings + admin UI. Write team_a_color (hex string) and team_a_image (Storage URL) to settings. Admin UI: color picker + file upload per team. Pro-only gate. Downstream: team header components across home, directory, scoreboard.

1
Revenue
Enforce limits at the action layer, not just tab-lock
Current gates only hide/lock admin tabs. A free user who discovers the API can bypass. Enforce limits inside the JS functions that write to DB — addPlayer(), addRound(), setTeamCount() — before the Supabase write. Limits enforced client-side with modal friction is sufficient for this SaaS stage.
Build: Read current count before write. Compare to tc.getLimit(plan, 'maxPlayers'). If at limit, call openUpgradeModal('Players') and return early. No DB writes needed for the check.
2
Data Model
Team metadata in settings table (short-term) → teams table (v2)
Storing team_a_color, team_a_image, team_a_captain_id as settings keys is consistent with the existing team_a_name pattern. It's the fastest path to ship. Long-term, a dedicated teams table with a FK to tournaments enables true unlimited teams, easier queries, and proper RLS per team.
Build: Ship v1 using settings keys (mirrors existing team_a_name pattern). Add 024_teams_table.sql migration in a later sprint for unlimited-team Pro architecture.
3
UX
Upgrade modal should show current usage vs. limit
When a free user hits the player limit, the modal should say "You have 24/24 players (Free plan limit). Upgrade to Pro for up to 120." This is much more compelling than the current generic "Setup tab is available on Pro." Contextual upgrade nudges convert at higher rates.
Build: Pass { feature, current, limit } to openUpgradeModal(). Render dynamic copy in the modal card.
4
Captain
Captain = player UUID in settings, displayed everywhere
Store team_a_captain_id as the player's UUID (from players.id). On load, join against the players array to get the name. This avoids denormalization drift where a player name change would break the displayed captain. The captain label surfaces on home.html team blocks and directory.html team cards.
Build: Admin dropdown in team column header: "Set Captain" → select from assigned players. Writes UUID. Home/directory resolve UUID to name at render time.
5
Storage
Team images via Supabase Storage, not inline base64
Team logos/images should be uploaded to a Supabase Storage bucket (team-images) and the public URL stored in team_a_image settings key. Base64 inline would bloat the settings table and slow all settings reads. Storage URLs also work with CDN caching and PWA asset caching.
Build: Create team-images bucket (public, read-all). Upload from admin.html via Supabase JS client. Store URL in settings. Pro-gated — only Pro plans can upload.
