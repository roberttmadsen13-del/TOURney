Tournament Creation
Create Flow Deep-Dive
⛳ 4-Step Wizard — What's in Each Step
  • Pre-step: Invite Code Gate — must enter a valid code before wizard renders. This is the #1 conversion killer for any cold traffic. No self-serve explanation. create.html:175-182
  • Step 1 — Account: sign in or sign up with email + password. New organizers need to create account here. No magic link option. create.html:203-207
  • Step 2 — Tournament Basics: name, slug, year, brand colors, logo. Slug availability async check. Logo optional. create.html:739-747
  • Step 3 — Format + Days: day count, format per day (12 options: stroke, scramble, best ball, shambles, stableford, match, alt shot, chapman, skins, greensomes, mod stableford, nassau). No "most popular" hint. High cognitive load for first-timers.
  • Step 4 — Launch: final review, create tournament. create.html:797-888 inserts tournament + settings to Supabase. launchAlert on error. No draft save.
🚨 Friction Points — Create Flow
  • HIGH Invite code gate before anything — no self-serve, no explanation, no "request access" fallback. Organizers who find the product organically hit a dead end.
  • MED Password auth on step 1 — new users must set and confirm a password. Magic link would eliminate this friction and the "forgot password" loop.
  • MED No wizard progress save — abandon at step 3 means full restart. Browser refresh = lost state.
  • MED 12 format options in step 3 with no guidance. "Stroke play" is the right default for most, but nothing indicates that.
  • LOW Slug auto-generation is smart, but the async availability check adds perceived latency without a clear loading indicator description in code.
  • LOW Error handling is present (launchAlert, authAlert, codeAlert) but relies on native alert() calls for slug validation errors — jarring UX.
What Could Be Removed or Deferred
  • Invite code gate — if this is intentional closed beta, add a "request access" form so cold traffic converts to a waitlist instead of bouncing. If beta is over, remove entirely.
  • Logo upload on step 2 — can be deferred to admin panel post-creation. Removes a step 2 blocker for organizers without a logo ready.
  • Brand color picker on step 2 — same deferral opportunity. Default theme works fine; let organizers customize later.
  • Format picker in step 3 — could default to "Stroke" with an optional override. Eliminates 90% of step 3 cognitive load.
  • Replace step 1 password auth with magic link — organizer enters email, gets a link, clicks it, continues wizard. No password to forget.
Player Onboarding
Player Join Flow — Friction Audit
How Players Join
  • Invite mechanism: organizer shares the tournament URL manually (copy/paste from browser or admin). No built-in "invite player" button that generates a personalized link. home.html is the landing point.
  • Player RSVP form fields: first name, last name, email, phone, handicap, available dates (conditional on reg_show_dates setting), why_me (essay field), trash_talk. Up to 8 fields. home.html:insert block
  • Required vs optional: not clearly differentiated in the UI. Players may not know what they can skip.
  • Account creation: separate step — player must then go to /login and create an account. This is a second distinct registration step after RSVP.
  • Critical bug: login.html:doSignUp() checks players table for the email before allowing account creation. A player who tries to sign up BEFORE submitting the RSVP form gets a hard error: "This email isn't registered as a player." Order dependency is invisible to the user.
Player Join Friction Ratings
  • LOW Tournament home page is publicly visible — no auth to see the event, read about it, view the field.
  • MED 7-8 RSVP fields is above industry average (typically 3-4 for event registration). "Why me" and "trash talk" are fun but add time.
  • MED Two-phase registration (RSVP then account creation) is non-standard. Most platforms combine these into one flow.
  • HIGH RSVP-before-account ordering is not communicated anywhere. Players who attempt login first hit a confusing hard error.
  • MED Password auth — golfers (often 40-60 demographic) have high password friction. Magic link or Google auth would significantly improve conversion.
  • LOW Post-RSVP confirmation is shown inline with a toast notification — good feedback, no page redirect needed.
First Use
First Scoring Experience
Scorecard Discoverability + Clarity
  • Discoverability: Scorecard is accessible from the nav (/t/:slug/scorecard) and linked from home.html nav. However, there is no prominent "Scoring is open — enter your scores" call-to-action on the home page when a round is active. A player landing on home during tournament day has to find the scorecard in the nav.
  • Scoreboard link: home.html:407 has a leaderboard link in nav and a "Full Leaderboard" gold button in the live-scores section. Leaderboard is well surfaced; scorecard entry is less so.
  • First-use clarity: Players who have never used TOURney need to understand format (stroke, scramble, etc.) before scoring. The format descriptions exist in the create flow but it's unclear if they're shown to players on the scorecard page itself.
  • Organizer awareness: No push notification or admin alert when a player starts entering scores — organizer visibility into "who's scored" relies on checking the leaderboard manually.
  • Hero scoreboard: home.html loads a live hero scoreboard pulling from scores + players tables — this is a great "scoring is happening" signal, but only after scores exist.
PWA Experience
Install Timing + Quality
PWA Install Analysis — install.html
  • Timing problem: install.html is a standalone dedicated page at /t/:slug/install. It is NOT automatically surfaced. Players must navigate to it intentionally or be linked by the organizer. This means most players never see the install prompt unless the organizer explicitly tells them to go there.
  • Prompt quality: The page correctly uses beforeinstallprompt to capture and defer the native browser prompt. Falls back to manual instructions after a delay if no prompt fires (correct for iOS). install.html:JS block
  • Already-installed detection: Checks display-mode: standalone and hides the install button if already installed. Smart.
  • What's missing: No automatic install banner or bottom sheet on first player visit to tournament home. No install prompt woven into the RSVP confirmation flow ("Get the app to track your scores"). The install page exists but is orphaned from the natural player journey.
  • Recommendation: Add a dismissible install banner to home.html after RSVP success — "Add TOURney to your home screen for instant scorecard access." Wire it to the same beforeinstallprompt event capture already in pwa.js.
Cold Start
Can You Understand TOURney Without an Account?
Pre-auth Product Clarity — marketing.html
  • Headline: "TOURney — Run Your Golf Tournament Like a Pro" — clear, audience-specific, benefit-oriented. Title tag matches.
  • Demo screens: marketing.html includes animated rotating demo screens (`.demo-screens`, `.demo-screen`) showing what the product looks like. This is a strong cold-start win — product is shown before any sign-up.
  • Feature presentation: Features section exists. Copy leans toward features (what it does) rather than pure benefits (what it means for you), but golf organizers are technical enough that this is acceptable.
  • Pricing visibility: No pricing visible on marketing page from what's indexed. First mention of billing/pricing appears at the invite code gate on /create. This is a gap — organizers don't know what they're buying into before starting the creation flow.
  • Social proof: No testimonials, no customer count, no "X tournaments run" stat visible in the evidence gathered. The stats section exists (`.stat-num`, `.stat-label`) but populates dynamically — may be empty on cold load.
  • Nav link to /platform: Exists but styled as near-invisible (very low opacity gold) — intentionally hidden from public? Fine for now but means no way for a prospect to see the platform dashboard.
Friction Removal Sprint
Sprint Plan — Prioritized by Conversion Impact
Ordered: highest abandonment risk first. Most items are day-of fixes, not architectural rewrites.
1
Fix: Login signup requires pre-existing RSVP — add clear error guidance
login.html:doSignUp() returns a hard error if email not in players table. Players who try to create an account before RSVPing get confused and abandon. This is a conversion-critical bug.
Fix: Replace generic error with "You need to register for the tournament first — scroll down on the event page to RSVP, then come back to create your account." Add a link back to the tournament home. Alternatively, allow account creation first and link it to the RSVP on submission.
2
Add "Request Access" to invite code gate on /create
Any organizer who discovers TOURney organically and clicks "Get Started" hits the invite code wall with no explanation and no exit path. 100% bounce rate for cold traffic.
Fix: Below the invite code field, add: "Don't have a code? Request early access →" linking to a simple Typeform, Google Form, or email mailto. Converts bounces to leads.
3
Surface PWA install after RSVP confirmation
install.html exists but is never surfaced in the natural player journey. Most players never install the PWA. Peak install intent is immediately after successful RSVP — player is excited, they're in.
Fix: After successRsvp shows, fire a dismissible install banner or modal: "Add TOURney to your home screen for instant scorecard access." Reuse the deferred prompt already captured in pwa.js.
4
Add "Next Steps" panel in admin after tournament creation
Post-creation, the organizer lands in admin with no guidance on what to do next. No onboarding checklist: add players, configure scoring, share the link.
Fix: First-time admin view (check localStorage flag gks_new_tournament) shows a 3-step checklist: (1) Copy & share your tournament link, (2) Configure scoring when ready, (3) Open scoring on tournament day. Dismiss once acknowledged.
5
Add scoring CTA to home.html when a round is active
Players landing on home during tournament day have no prominent signal that scoring is open and where to go. Leaderboard is surfaced; scorecard entry is not.
Fix: When play_status = 'active', show a sticky gold banner or hero button on home.html: "Scoring is Open — Enter Your Scores →" linking to /scorecard. Conditional on tournament status already available in the tourney context.
6
Reduce RSVP form to essential fields; mark optional fields clearly
7-8 fields in the RSVP form is above average for event registration and increases form abandonment. "Why me" and "trash talk" are delightful but optional — they're not labeled as such.
Fix: Add (optional) label to why_me, trash_talk, phone fields. Consider collapsing optional fields behind a "Add more info" expander. Required minimum: first name, last name, email.
7
Add format recommendation to create step 3
12 format options with no guidance creates decision paralysis. Most first-time organizers want stroke play. Nothing signals this.
Fix: Mark "Stroke" with a Most Popular badge. Add a one-line description under each selected format (already exists in FMT_DESC on home.html — port to create.html). Default selection to Stroke.
8
Add pricing transparency to marketing.html
No pricing is visible before starting the create flow. Organizers don't know what they're committing to. Trust gap.
Fix: Add a simple pricing section to marketing.html: "First tournament free during beta — then $X/tournament or $Y/year." Even a "Pricing" link in the nav that scrolls to a brief callout removes the ambiguity.
9
Replace password auth with magic link (organizer + player)
Password auth is the highest-friction login pattern. Golf organizers (and golfers) are not known for password hygiene. Magic link removes the "forgot password" loop entirely. Both login.html and create.html step 1 use password.
Fix: Supabase supports auth.signInWithOtp() — swap both flows to magic link. Keep password as fallback for users who've already set one. This is a 1-day migration with high conversion impact.
